# Коннекторы ingest: CRM/ERP → event log OrgTwin

Документ для пилота: как сопоставить поля Битрикс24 / 1С / SAP с плоским event log и что спросить у заказчика до живого доступа.

Живые коннекторы **вне v1**. В коде — каркасы `Bitrix24Adapter`, `OneCAdapter`, `SapAdapter`, `SqlEventSource` (`dry_run()` без секретов). Рабочий путь S1: загрузка **CSV / XES** через реестр `data/uploads/`.

---

## 1. Минимальный контракт события

| Поле OrgTwin | Обязательно | Смысл |
|---|---|---|
| `case:concept:name` | да | Идентификатор кейса (сделка, документ, заявка) |
| `concept:name` | да | Действие / стадия / операция |
| `time:timestamp` | да | Время события (предпочтительно UTC) |
| agent-col (`org:resource` по умолчанию) | да | Исполнитель: человек, роль или отдел |
| context (опц.) | нет | Сумма, приоритет, возраст, категория |

Интерфейс источника: `EventSource.load()` и опционально `pull(fit_start, fit_end)`.

CSV-маппинг по умолчанию (`CsvEventsAdapter`):

```text
case_id → case:concept:name
activity → concept:name
timestamp → time:timestamp
agent → org:resource
```

## 2. Битрикс24

### Типичные источники

| Источник | Case | Activity | Timestamp | Agent |
|---|---|---|---|---|
| CRM-сделка + история стадий | `DEAL_ID` / `ID` | `STAGE_ID` | `CREATED_TIME` / `DATE_MODIFY` | `ASSIGNED_BY_ID` |
| Задачи | `ID` / `GROUP_ID`+`ID` | статус / тип | `CREATED_DATE` / `CHANGED_DATE` | `RESPONSIBLE_ID` |
| Смарт-процесс (SPA) | `id` элемента | `stageId` | даты из таймлайна | ответственный / UF |

### Что нужно от ИТ

1. Входящий **webhook** или приложение с OAuth.
2. Права чтения CRM / задач / нужного SPA.
3. Понимание: агент = пользователь или отдел (`UF_*` / подразделение).
4. Часовой пояс портала и полнота истории стадий (не только текущая).

`Bitrix24Adapter(config).dry_run()` возвращает ожидаемую схему без вызова API.

## 3. 1С

### Типичные источники

| Источник | Case | Activity | Timestamp | Agent |
|---|---|---|---|---|
| Документ (заказ, реализация) | `Ссылка` / номер | статус / вид операции | `Дата` / `ДатаИзменения` | `Ответственный` |
| Бизнес-процесс | экземпляр БП | точка маршрута | дата точки | исполнитель |
| Регистр сведений / журнал | измерение-ключ | ресурс/статус | период | автор |

### Что нужно от ИТ

1. Публикация **OData** или HTTP-сервиса (URL).
2. Учётка только на чтение (логин/пароль или токен).
3. Имя объекта (`Документ.ЗаказКлиента` и т.п.) и реквизиты статуса/ответственного.
4. Политика PII и объём выгрузки (месяцы истории).

`OneCAdapter(config).dry_run()` — схема без секретов в git.

## 4. SAP (ECC / S/4HANA)

### Типичные источники

| Источник | Case | Activity | Timestamp | Agent |
|---|---|---|---|---|
| Закупка / PO | `EBELN` (+ позиция) | статус / тип изменения | change timestamp | `UNAME` |
| Workflow / work item | Object ID / WI_ID | `WI_STAT` / activity | `WI_CD`+`WI_CT` | agent |
| Change documents | object key | change indicator | utime | username |

### Что нужно от ИТ

1. Канал: **OData** и/или RFC destination.
2. Client, user, password (или OAuth) — только чтение.
3. Бизнес-объект пилота (`purchase_order`, `BUS2012`, …).
4. Согласование маскирования user id и объёма (fit/hold окна).

`SapAdapter(config).dry_run()` — ожидаемые колонки и ключи конфига.

## 5. Чеклист пилота (спросить у клиента)

1. Есть ли выгрузка событий за **≥ 5–12 месяцев** (цель протокола 7+3)?
2. Кто «агент»: человек, роль или отдел? Стабилен ли id агента?
3. Есть ли **стабильный case id** на всём жизненном цикле?
4. Часовой пояс и полнота timestamps (дыры, будущие даты)?
5. PII: что маскировать до передачи (ФИО, телефоны, ИНН)?
6. Объём: оценка числа событий / кейсов; уложится ли в лимит upload (~80 МБ)?
7. Контакт админа системы на коннектор и окно тестового доступа.
8. Можно ли сначала отдать **анонимизированный CSV/XES** без live API?

### Критерии готовности к ingest

- [ ] Файл/выборка читается адаптером без ошибок схемы.
- [ ] `ingest_report`: разумные `n_events` / `n_cases` / `n_agents`, `unknown_frac` не доминирует.
- [ ] `span_days` покрывает выбранные `fit_months` + `holdout_months`.
- [ ] В UI виден `split_meta` (границы fit/hold).
- [ ] Демо-доноры BPIC/Hospital не затронуты (изоляция `data/uploads/`).

## 6. Песочница upload (S1)

| Элемент | Путь / правило |
|---|---|
| Файлы | `data/uploads/{donor_id}/` |
| Реестр | `data/uploads/registry.json` |
| Лимит | `MAX_UPLOAD_BYTES = 80_000_000` |
| API-слой | `OrgModelStore.register_upload` / `delete_upload` |
| Отчёт | поле `ingest` в OrgModel |

До живого доступа заказчика — только CSV/XES + скелеты коннекторов.
